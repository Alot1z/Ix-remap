## Problem

`scripts/install-skill.sh` installs the Ix skill into agent harnesses, but everything around it is manual: discovering which harnesses exist, choosing *what* to install (skill only? CLI? MCP server? an editor plugin?), and running several different installers for the surrounding ecosystem. A user with four harnesses reads four READMEs and runs four commands with four different shapes.

## Proposal: one interactive installer entry point

An optional interactive `ix install` (or `npx @ix/cli install` once the package ships) that opens with the Ix banner and walks the user through a short menu:

```
  ██ Ix

  Detected harnesses: claude, agents, codex, cursor

  ? What should this machine get?
    [x] Ix skill        → .claude/.agents/.codex/.cursor (4 found)
    [ ] Ix CLI          → PATH install, version pinning
    [ ] MCP server      → harness config wiring (stdio)
    [ ] Editor plugins  → where a plugin marketplace exists

  → writes nothing until you confirm; --dry-run available
```

Design constraints carried over from the merged installer:

- **Same harness registry** as `ix-cli/scripts/skill-harnesses.mjs` — one source of truth for the four verified conventions, reused by both the interactive and the scripted paths.
- **Interactive is a pre-fill, never a different engine**: every menu choice maps onto the existing non-interactive flags (`--dry-run`, explicit harness ids, `--json`). CI keeps grepping raw lines; automation is unaffected.
- **JSON mode parity**: `--json` on the interactive run emits the same per-host decision report the scripted installer emits, so both paths are machine-auditable.
- **Refusal guard unchanged**: a foreign same-name skill is never silently overwritten, interactive or not.

## Why now

The building blocks all exist on main: the harness registry, the installer's UX discipline (dry-run/JSON/labels/refusal parity), the MCP harness surface, and the CLI's own install path. This proposal only adds the menu that composes them, so the scope is UX wiring over verified parts, not new install machinery.

## Non-goals (for a first version)

- No new install backends — the curl/homebrew/npm zero-clone paths stay as documented; the interactive installer assumes a repo or package context.
- No auto-detection beyond what `skill-harnesses.mjs` already verifies.
- No colored/spinner output — CI greps raw lines.

## Evidence

From a hermetic demo run of the merged installer (2026-09-05, recorded transcript): the four-harness install path, `--dry-run` previews, and the `--json` decision report all behave as described above; the menu proposal only pre-selects among behaviors already shipped. A working sketch of the output polish half of this exists and can be contributed if the direction sounds right.
